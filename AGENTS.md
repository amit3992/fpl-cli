# AGENTS.md

Guidance for AI coding agents working **on** the `fpl-cli` codebase.

> Note: [`CONTEXT.md`](./CONTEXT.md) is a different document — it instructs agents (and humans) on how to **use** the published `fpl` CLI as a tool. This file is about **editing the code**.

## Project summary

`fpl-cli` is a TypeScript CLI for Fantasy Premier League. It wraps the undocumented FPL web API (`fantasy.premierleague.com/api`) and the PingOne DaVinci OAuth flow (`account.premierleague.com`). Published as `@amit3992/fpl-cli` on GitHub Packages; also distributed via Homebrew. Designed for dual human + AI-agent use — every command supports `--json` output and most mutating commands are dry-run by default.

## Tech stack

- **Language:** TypeScript, strict mode, ESM-only (`"type": "module"`, `module: Node16`).
- **Node:** `>=18` (uses global `fetch`, `node:crypto` webcrypto-style APIs, `node:readline/promises`).
- **CLI framework:** `commander@12`.
- **Terminal output:** `chalk@5`, `cli-table3`.
- **Dev:** `tsx` (run from source), `tsc` (build). No bundler.
- **No tests, no linter, no formatter configured.** See "Testing" below.

## Commands

```bash
npm install          # install deps
npm run build        # tsc → dist/  (required before publish via prepublishOnly)
npm run dev -- <cmd> # run from source via tsx, e.g. `npm run dev -- team --json`
npm start -- <cmd>   # run compiled dist/index.js
npm run dev -- doctor --json   # sanity check config + API connectivity
```

The published binary is `fpl` → `./dist/index.js` (declared in `package.json` `bin`). When testing changes locally without publishing, prefer `npm run dev -- <args>`.

## Architecture & invariants

### Layering (do not break)

```
index.ts  →  commands/*  →  api / auth / config  →  scoring / validate / fields / output
```

- `commands/*` is the orchestration layer: parse args/options, call `api`/`auth`/`config`, format via `output`. Commands should not contain API URL strings, scoring math, or config file paths.
- `api.ts` owns **all** HTTP to `fantasy.premierleague.com` and all shared types. `auth.ts` owns **all** HTTP to `account.premierleague.com` plus token persistence. Do not `fetch()` FPL endpoints from `commands/`.
- `scoring.ts`, `validate.ts`, `fields.ts`, `output.ts` are **pure** (no I/O, no network). Keep them that way — they're the testable core.
- `output.ts` is the single source of console output. Use `printJson` / `printError` / `makeTable`. Do not call `console.log` directly with raw JSON or hand-rolled tables in commands.

### Output contract

- Every command takes an `asJson: boolean` first-ish param and branches on it.
- **Errors:** always go through `printError(message, asJson)` → emits `{"error": ...}` in JSON mode or red `Error: ...` in human mode, then `process.exit(1)`. Never `throw` out of a command action; commander won't format it as the JSON contract.
- **Success JSON:** `printJson(data)`. Apply `--fields` projection via `filterFields(data, fields)` immediately before printing.
- Human mode uses `chalk` colors + `makeTable`. Keep table column counts consistent with `head`.

### Dry-run / confirm convention

- `transfers execute` and `chip` are **dry-run by default**; `--confirm` mutates.
- Always return a structured object (`mode: "dry_run" | "confirmed"`, plus the relevant fields) so `--json` consumers can branch.
- `CONTEXT.md` documents these invariants for end users — keep that doc in sync if you change behavior.

### Live vs historical squad

`api.getLiveSquadState()` returns `{ source: "live" | "historical", caveat: string | null, gameweek, picks, bank, team_value, chips }`.

- `"live"` — authenticated via `getMySquad` (`/my-team/<id>/`); reflects pending transfers/captain/chip.
- `"historical"` — fallback via `getMyTeam` (`/entry/<id>/event/<gw>/picks/`); locked picks.
- `caveat: "no_auth_pending_changes_unknown"` — user not logged in; pending changes invisible. Commands must surface this so callers know to `fpl login`.

Do not silently drop `source`/`caveat` from command output — they are part of the API contract.

### Auth

- Tokens live in `~/.config/fpl-cli/tokens.json` (chmod `0o600`).
- `getAccessToken()` auto-refreshes expired access tokens using the refresh token; returns `null` if no tokens or refresh fails. Commands should treat `null` as "not logged in" and `printError("Not logged in. Run: fpl login", asJson)` — do not attempt to re-prompt for credentials mid-command.
- The DaVinci flow in `auth.ts` is reverse-engineered and brittle. If login breaks, the failure is almost certainly a change in FPL's PingOne flow (step shape, `eventName`, `actionKey`, `code` field). Compare a browser HAR capture against `login()`'s step sequence before changing logic.

### Config

- `~/.config/fpl-cli/config.json` stores `FPL_TEAM_ID`, `FPL_EMAIL`, `FPL_PASSWORD`. **The password is stored in plaintext** (file is `0o600`). This is a known limitation — see "Known issues" below. Don't add new secrets to this file without considering storage.

## Adding a new command

1. Create `src/commands/<name>.ts` exporting an `async function <name>Command(asJson: boolean, ...)`. Follow the existing pattern: validate inputs → call `api`/`auth`/`config` → format via `output` → `printJson` or human table.
2. If it needs a new API endpoint, add the typed fetcher + interface to `api.ts` (use `get`/`authGet`/`authPost` helpers — do not open a raw `fetch`). If it needs scoring, add to `scoring.ts`.
3. Register it in `src/index.ts` with `program.command(...)` / `<parent>.command(...)`. Mirror the option conventions: `--json` is global (read via the `json()` helper), `--fields` is per-command for list/detail output, `--input-json` for any command that takes structured transfer/chip-like input.
4. If the command mutates state (transfers, captain, chips), **default to dry-run** and require `--confirm`. Return `mode` in the JSON output.
5. Update `README.md` (usage section) and `CONTEXT.md` (quick reference + invariants) if the surface changes. These are contracts for users and agents.
6. Run `npm run build` — it must pass with zero errors under `strict`.

## Gotchas

- **`module: Node16` requires `.js` extensions in relative imports** (`import { x } from "./api.js"`). Don't drop the extension or use extensionless imports — `tsc` will error.
- **`commander` option names:** `--team-id` → `opts.teamId` (camelCase). Keep this mapping in mind when adding options.
- **`getBootstrap()` caches in-process only.** Each CLI invocation re-fetches `/bootstrap-static/`. Don't rely on cross-invocation caching; it doesn't exist.
- **FPL player IDs are integers** (`element`). Player *names* in args are resolved via `getPlayerByName` (exact → substring → Dice ≥0.5). Always go through that function; don't hand-resolve.
- **Prices** are stored as integers ×10 (`now_cost`, `selling_price`, `bank`). Divide by 10 for display/JSON. Several commands already do this — match the convention.
- **Position codes:** `1=GKP, 2=DEF, 3=MID, 4=FWD`. Status codes: `a/d/i/s/u`. Both maps are duplicated across `team.ts`, `player.ts`, `news.ts` — if you add a new one, consider extracting to a shared constants module, but don't refactor casually (keep diffs focused).
- **`makeTransfer` with `transfers: []`** is used to arm wildcard/freehit via the transfers endpoint. This is intentional but relies on undocumented API behavior; preserve it unless FPL changes.
- **Chip activation paths differ by chip type:** `bboost`/`3xc` (lineup chips) go through `updateMyTeam` with the chip name; `wildcard`/`freehit` (structural chips) go through `makeTransfer`. See `chipCommand`.
- The repo includes a built `*.tgz` (gitignored) and `dist/` (gitignored). Don't commit build artifacts.

## Testing

There are currently **no automated tests**. The pure modules (`scoring.ts`, `fields.ts`, `validate.ts`, and the `diceCoefficient`/`getPlayerByName` logic in `api.ts`) are the highest-value targets if you add tests. If you introduce a test runner (vitest is the natural fit for ESM + TS), add it to `devDependencies`, a `test` script, and a `tests/` directory, and document it here. Do not add a runner without wiring a `npm test` script.

When fixing a bug or adding non-trivial logic in the pure modules, strongly consider adding a regression test even if a suite doesn't yet exist — it's cheap and the functions are deterministic.

## Known issues / improvement targets

If you're looking for work, these are real gaps (verify they still apply before starting):

- **No tests, no lint, no format config.**
- **Plaintext `FPL_PASSWORD` in config.json.** Could be dropped after a successful `login` since OAuth tokens are what's actually used.
- **No retry/backoff in `api.ts`** — FPL occasionally 429s. A small wrapper around `get`/`authGet`/`authPost` would help agent-driven loops.
- **`news` (squad-wide) uses historical picks** (`getMyTeam`), not live squad — inconsistent with `team`'s live-first behavior.
- **`chip` dry-run for `none`** doesn't pre-check that a chip is armed, so `--confirm` can fail after a successful dry-run.
- **Position/status maps duplicated** across three command files.
- **Cross-invocation bootstrap cache** could cut latency for agent-driven multi-call workflows (short-TTL file cache).

## Publishing

- `npm publish` runs `prepublishOnly` → `npm run build`. Publishing target is GitHub Packages (`publishConfig.registry = https://npm.pkg.github.com`, scoped `@amit3992`). `.npmrc` maps that scope to the GitHub registry. Auth for publish uses a GitHub PAT in npm config — don't commit credentials.
- Homebrew tap is a separate repo (`amit3992/tap`); updating the brew formula is outside this repo's automation.

## When in doubt

- Match the closest existing command's structure rather than inventing a new pattern.
- Prefer adding to `api.ts`/`scoring.ts` over inlining logic in a command.
- Keep `CONTEXT.md` and `README.md` truthful — they are contracts, not commentary.
- If the FPL API or auth flow changes, fix it in `api.ts`/`auth.ts` and leave command signatures stable; callers (including `CONTEXT.md` workflows) depend on the CLI surface, not the HTTP surface.
